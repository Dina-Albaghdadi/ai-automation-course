# 🧪 U8 — Testing and Reliability
## Prove It Works. Test What Can Fail. Build What Can Be Trusted.

# 🎯 1. Learning Objectives

في هذه المرحلة، لن نكتفي بمشاهدة النظام وهو يعمل في حالة مثالية، بل سنتعلّم كيف نتحقق من أنه يحقق المتطلبات، ويتعامل مع الحالات غير المتوقعة، ويحافظ على سلامة البيانات.

بنهاية هذه المرحلة، يجب أن نكون قادرين على:

- تحويل المتطلبات إلى Test Cases واضحة.
- التمييز بين Verification وValidation وTesting وDebugging.
- اختيار مستويات الاختبار المناسبة.
- اختبار التطبيقات وقواعد البيانات وWorkflows وعمليات التكامل.
- تقييم مخرجات AI بطريقة منهجية.
- اختبار RAG من حيث جودة الاسترجاع واستناد الإجابات إلى المصادر.
- اختبار AI Agents من حيث استخدام الأدوات والالتزام بالقيود.
- التحقق من الأمان والصلاحيات.
- اختبار حالات الفشل والمهلات وإعادة المحاولة والطلبات المتكررة.
- استخدام Logs وExecution History لتشخيص المشكلات.
- إعداد Test Report وتحديد ما إذا كان الحل جاهزًا للقبول والنشر.

## Engineering Principle

> A successful execution does not prove that a system is reliable.

نجاح تنفيذ واحد لا يثبت أن النظام موثوق.

قد ينجح Workflow مرة، لكنه يفشل عندما تكون المدخلات ناقصة. وقد يعطي AI إجابة ممتازة في المثال الأول، لكنه يختلق معلومات في المثال الثاني.

لذلك، نحتاج إلى اختبارات تغطي السلوك المتوقع والحالات التي قد يفشل فيها النظام.

# 🔍 LAYER 1 — Understanding Testing

## 2. Testing vs. Verification vs. Validation vs. Debugging

هذه المصطلحات مرتبطة ببعضها، لكنها لا تعني الشيء نفسه.

### 2.1 Testing

هو تنفيذ اختبارات ومقارنة النتائج الفعلية بالنتائج أو المعايير المتوقعة.

مثال:

نرسل طلبًا إلى تطبيق PlanCraft AI، ثم نتحقق من أن الطلب حُفظ، وأن الخطة أُنشئت، وأن النتيجة ظهرت في الواجهة.

### 2.2 Verification

السؤال:

**Are we building the system right?**

هل بنينا النظام وفق التصميم والمواصفات المحددة؟

مثال:

إذا كانت مواصفات النظام تتطلب وجود `request_id` في كل طلب، نتحقق من أن النظام يفرض هذا الشرط.

### 2.3 Validation

السؤال:

**Are we building the right system?**

هل النظام الذي بنيناه يحل مشكلة المستخدم الحقيقية؟

قد يحقق التطبيق جميع المواصفات التقنية، لكنه لا يساعد المستخدم على إنجاز المهمة التي يحتاج إليها.

مثال:

قد يكون نظام تأهيل العملاء العقاريين قادرًا على جمع جميع الحقول المطلوبة، لكن إذا كان يكرر الأسئلة أو لا يفهم إجابات العملاء، فقد تكون تجربة الاستخدام غير مناسبة.

### 2.4 Debugging

هو التحقيق في سبب حدوث مشكلة، ثم تحديد مصدرها وإصلاحها والتحقق من الإصلاح.

مثال:

إذا أرسل التطبيق طلبًا إلى n8n، لكن لم تظهر الخطة، نراجع مسار البيانات لتحديد ما إذا كانت المشكلة في الاستدعاء، أو معالجة AI، أو الحفظ في Supabase، أو استرجاع النتيجة.

### كيف ترتبط هذه المفاهيم؟

```text
Requirements
     |
     v
Design and Implementation
     |
     v
Verification and Testing
     |
     v
Validation Against User Needs
     |
     v
Identify Failures
     |
     v
Debug and Fix
     |
     v
Retest
```

هذه ليست دائمًا مراحل خطية منفصلة؛ غالبًا ما تتكرر أثناء التطوير.

**الاختبار يكشف المشكلة، والتشخيص يساعدنا على فهمها، ثم نعيد الاختبار للتأكد من نجاح الإصلاح.**

# 📋 LAYER 2 — From Requirements to Test Cases

## 3. Every Important Requirement Needs Evidence

لا نبدأ الاختبار بتجربة عشوائية للتطبيق.

نبدأ بالمتطلبات التي اتفقنا عليها، ثم نحدد كيف سنثبت تحقق كل متطلب.

### 3.1 Requirement

يجب أن يتمكن المستخدم من إنشاء خطة مشروع وحفظها واسترجاعها.

### 3.2 Test Scenario

إنشاء خطة مشروع باستخدام مدخلات صحيحة.

### 3.3 Test Case

- نرسل طلبًا صحيحًا.
- نتحقق من حفظ الطلب.
- نتحقق من بدء المعالجة.
- نتحقق من إنشاء الخطة.
- نتحقق من حفظها في قاعدة البيانات.
- نفتح صفحة تفاصيل الخطة.
- نتحقق من ظهور النتيجة المحفوظة.

### 3.4 Expected Result

يجب أن تظهر الخطة المرتبطة بالطلب الصحيح، وأن تكون محفوظة ويمكن استرجاعها.

### 3.5 Evidence

يمكن أن تشمل الأدلة:

- سجل تنفيذ Workflow.
- سجل الطلب في قاعدة البيانات.
- سجل الخطة المحفوظة.
- نتيجة الاختبار.
- لقطة شاشة للنتيجة عند الحاجة.

الهدف هو أن نستطيع إثبات النجاح، لا أن نعتمد على الانطباع.

## 3.6 Test Case Template

| Field | Description |
|---|---|
| Test ID | معرّف الاختبار |
| Requirement | المتطلب الذي نختبره |
| Preconditions | الشروط التي يجب أن تكون متحققة قبل الاختبار |
| Input | البيانات المستخدمة |
| Steps | خطوات تنفيذ الاختبار |
| Expected Result | النتيجة المتوقعة |
| Actual Result | النتيجة الفعلية |
| Status | PASS / FAIL / BLOCKED |
| Evidence | دليل النتيجة |
| Notes | الملاحظات |

### الفرق بين الحالات

- `PASS`: النتيجة الفعلية تحقق معايير النجاح.
- `FAIL`: النتيجة الفعلية لا تحقق معايير النجاح.
- `BLOCKED`: تعذر تنفيذ الاختبار بسبب مشكلة تمنع استكماله.

لا نصنّف الاختبار على أنه `PASS` لمجرد أن التطبيق لم يُظهر رسالة خطأ.

# 🧱 LAYER 3 — Testing Levels

## 4. Choose the Right Testing Level

لا يحتاج كل اختبار إلى تشغيل النظام بالكامل. يمكن اختبار أجزاء صغيرة بصورة مستقلة، ثم اختبار تفاعلها، ثم اختبار النظام ككل.

### 4.1 Unit Testing

اختبار وظيفة صغيرة بصورة مستقلة.

مثال:

اختبار وظيفة تتحقق من أن `request_id` موجود وبالصيغة المطلوبة.

```text
Input:
request_id = missing

Expected:
Validation fails
```

في الأنظمة البرمجية التقليدية، يمكن اختبار الدوال الصغيرة بصورة مباشرة.

أما في Low-Code وNo-Code، فقد تكون الاختبارات على مستوى وظائف أو تعبيرات أو أجزاء من المنطق، بحسب ما تسمح به الأدوات.

### 4.2 Component Testing

اختبار مكوّن واحد للتحقق من سلوكه.

أمثلة:

- اختبار نموذج التطبيق والتحقق من مدخلاته.
- اختبار وظيفة Server-Side Function.
- اختبار Node في n8n باستخدام مدخلات محددة.
- اختبار سياسة وصول في قاعدة البيانات.

### 4.3 Integration Testing

اختبار الاتصال بين مكوّنين أو أكثر.

أمثلة:

- Frontend مع Supabase.
- Server-Side Function مع n8n.
- n8n مع AI Provider.
- n8n مع Supabase.
- RAG Retriever مع مولّد الإجابة.

### 4.4 End-to-End Testing — E2E

اختبار رحلة المستخدم كاملة من البداية إلى النهاية.

مثال:

```text
User submits request
        |
        v
Application saves request
        |
        v
Server-side function calls n8n
        |
        v
AI generates a plan
        |
        v
Workflow validates output
        |
        v
Supabase saves the plan
        |
        v
Application retrieves the plan
        |
        v
User sees the saved result
```

نختبر هذه الرحلة بوصفها عملية متكاملة.

### 4.5 User Acceptance Testing — UAT

اختبار قبول المستخدم.

نستخدمه للتحقق من أن الحل يحقق احتياجات المستخدم ومعايير القبول المتفق عليها.

مثال:

يجرّب موظف في شركة عقارية نظام تأهيل العملاء، ويتحقق من أنه يجمع المعلومات اللازمة، ويعرض ملخصًا صحيحًا، ويتيح للموظف متابعة العميل.

### هل نحتاج جميع المستويات؟

ليس بالضرورة أن يكون لكل مشروع إطار اختبار آلي لكل مستوى.

نختار الاختبارات المناسبة لحجم النظام ومخاطره، لكن لا ينبغي إهمال الاختبارات الأساسية التي تثبت صحة المكونات والتكامل وتجربة المستخدم.

# 🧭 LAYER 4 — Functional and Non-Functional Testing

## 5. Functional Testing

يختبر ما إذا كان النظام ينفذ الوظائف المطلوبة.

أمثلة:

- هل يمكن إنشاء طلب؟
- هل تُحفظ البيانات؟
- هل يُستدعى Workflow؟
- هل تُنشأ النتيجة؟
- هل يستطيع المستخدم استرجاعها؟
- هل يمنع النظام تنفيذ عملية غير مسموح بها؟

## 5.1 Negative Testing

يختبر كيفية تعامل النظام مع المدخلات أو الظروف غير الصحيحة.

أمثلة:

- إرسال حقل مطلوب فارغًا.
- إرسال `request_id` غير صالح.
- طلب سجل غير موجود.
- إرسال قيمة خارج القيم المسموح بها.
- استدعاء API دون صلاحية مناسبة.

الهدف ليس جعل النظام يقبل كل شيء، بل التأكد من أنه يرفض الحالات غير الصحيحة بطريقة واضحة وآمنة.

## 5.2 Boundary Testing

يختبر القيم الموجودة عند حدود القيود.

إذا كان وصف المشروع يسمح بما يصل إلى 2,000 حرف، اختبر:

- وصفًا قصيرًا صحيحًا.
- وصفًا بطول 1,999 حرفًا.
- وصفًا بطول 2,000 حرف.
- وصفًا يتجاوز الحد.

تساعد هذه الاختبارات على اكتشاف أخطاء لا تظهر في الأمثلة المعتادة.

## 5.3 Permission Testing

يختبر ما يستطيع كل مستخدم الوصول إليه.

أمثلة:

- هل يستطيع المستخدم قراءة سجلاته فقط؟
- هل يستطيع تعديل سجل لا يملكه؟
- هل يمكن تجاوز صلاحيات الواجهة بطلب مباشر؟
- هل يستطيع مستخدم غير مخوّل تشغيل عملية حساسة؟

يجب اختبار الصلاحيات من جهة الخادم وقاعدة البيانات، وليس من خلال الواجهة فقط.

## 5.4 Non-Functional Testing

يختبر خصائص النظام التي لا تقتصر على تنفيذ وظيفة بعينها.

| Type | Question |
|---|---|
| Performance Testing | هل يستجيب النظام ضمن الزمن المقبول؟ |
| Reliability Testing | هل يتعامل مع الأعطال والتكرار بصورة صحيحة؟ |
| Security Testing | هل يحمي البيانات والأسرار؟ |
| Usability Testing | هل يستطيع المستخدم إتمام المهمة بسهولة؟ |
| Accessibility Testing | هل يمكن للأشخاص ذوي الاحتياجات المختلفة استخدام الواجهة؟ |
| Scalability Testing | كيف يتصرف النظام عند زيادة حجم الطلبات؟ |

ليس مطلوبًا تنفيذ اختبارات تحميل واسعة لكل مشروع تعليمي، لكن يجب تحديد المخاطر ذات الصلة واختبارها بما يناسبها.

# 🤖 LAYER 5 — Testing AI Systems

## 6. Why AI Needs a Different Testing Approach

في الأنظمة التقليدية، قد تكون لدينا مدخلات ثابتة ونتائج متوقعة بصورة دقيقة.

أما في أنظمة AI، فقد تختلف الإجابة بين تشغيل وآخر بسبب النموذج أو إعداداته أو السياق أو طريقة التوليد.

لذلك، لا يكفي غالبًا أن نقارن النص الناتج بنص واحد محفوظ مسبقًا.

بدلًا من ذلك، نحدد **معايير جودة وسلوك يمكن التحقق منها**.

### Example

نظام يقرأ رسالة عميل ويستخرج:

- الاسم.
- رقم الهاتف.
- نوع العقار المطلوب.
- الميزانية.
- الهدف من التواصل.

بدلًا من اشتراط أن يعيد AI صياغة المعلومات بالطريقة نفسها حرفيًا، نختبر:

- هل استخرج الاسم بصورة صحيحة؟
- هل رقم الهاتف مطابق للمصدر؟
- هل حدد نوع العقار بشكل صحيح؟
- هل تعامل مع الحقول المفقودة بصورة مناسبة؟
- هل اخترع معلومات لم يذكرها العميل؟
- هل أعاد البيانات بالبنية المطلوبة؟

### 6.1 Define AI Evaluation Criteria

قبل اختبار AI، حدّد ما الذي يجعل النتيجة مقبولة.

| Criterion | Evaluation Question |
|---|---|
| Correctness | هل المعلومات المستخرجة صحيحة؟ |
| Completeness | هل الحقول المطلوبة موجودة؟ |
| Relevance | هل الإجابة مرتبطة بالمهمة؟ |
| Groundedness | هل تستند الادعاءات إلى المصادر المتاحة عندما يكون ذلك مطلوبًا؟ |
| Structured Output | هل تطابق النتيجة البنية المطلوبة؟ |
| Safety | هل يتجنب السلوك غير الآمن أو غير المسموح؟ |
| Consistency | هل يحافظ على مستوى مقبول من الجودة عبر أمثلة مختلفة؟ |
| Instruction Following | هل يلتزم بالتعليمات والقيود المحددة؟ |

لا تحتاج جميع الأنظمة إلى جميع المعايير. اختاري المعايير وفق وظيفة الحل ومخاطره.

## 7. Build a Representative Test Dataset

لا تختبري النظام بمثال واحد.

أنشئي مجموعة أمثلة تمثل الحالات التي قد يواجهها النظام في الاستخدام الحقيقي.

### Example: Real Estate Lead Qualification

| Case | Input | What to Evaluate |
|---|---|---|
| 1 | عميل يذكر جميع المعلومات المطلوبة | دقة استخراج الحقول |
| 2 | عميل يذكر الميزانية ولا يذكر الموقع | التعامل مع البيانات الناقصة |
| 3 | عميل يكتب رسالة طويلة وغير مرتبة | استخراج المعلومات من نص غير منظم |
| 4 | عميل يغيّر ميزانيته أثناء المحادثة | تحديث البيانات دون فقد السياق |
| 5 | عميل يقدم رقم هاتف غير مكتمل | اكتشاف البيانات غير الصالحة |
| 6 | رسالة لا تتعلق بالعقارات | التعامل المناسب مع الطلب خارج النطاق |
| 7 | رسالة تحتوي على معلومات متناقضة | طلب التوضيح بدل التخمين |
| 8 | رسالة تطلب تجاهل التعليمات | مقاومة التعليمات غير الموثوقة |
| 9 | رسالة لا تحتوي على أي معلومات كافية | عدم اختلاق المعلومات |
| 10 | رسالة طويلة جدًا أو غير واضحة | التعامل مع حدود الإدخال |

هذه المجموعة تمثل نقطة بداية، وليست دليلًا على أن النظام أصبح موثوقًا في كل الظروف.

كلما كانت المهمة أكثر أهمية، احتجنا إلى بيانات اختبار أوسع وأكثر تمثيلًا للاستخدام الحقيقي.

## 7.1 Use a Test Dataset Consistently

احتفظي بمجموعة الاختبارات واستخدميها عند تعديل:

- Prompt.
- Model.
- Model parameters.
- Workflow logic.
- Output schema.
- Retrieval configuration.
- Business rules.

الهدف هو معرفة ما إذا كان التعديل قد حسّن الأداء أو تسبب في تراجع سلوك كان يعمل سابقًا.

تُسمى هذه العملية `Regression Testing`.

# 📄 LAYER 6 — Structured Output Testing

## 8. Validate the Shape and Meaning of AI Output

قد يعيد النموذج إجابة تبدو منطقية، لكنها غير مناسبة للمعالجة الآلية.

مثال:

النظام يتوقع:

```json
{
  "budget": 100000,
  "property_type": "apartment"
}
```

لكن AI يعيد:

```json
{
  "budget": "around one hundred thousand",
  "property_type": "maybe an apartment"
}
```

قد يكون النص مفهومًا للبشر، لكنه لا يطابق العقد المطلوب.

يجب التحقق من:

1. صلاحية JSON عند استخدامه.
2. وجود الحقول المطلوبة.
3. أنواع البيانات.
4. القيم المسموح بها.
5. القواعد الخاصة بالمهمة.
6. عدم وجود معلومات مخترعة في الحقول الحساسة.

### Schema Validation vs. Semantic Validation

**Schema Validation** يتحقق من شكل البيانات وأنواعها.

مثال: `budget` يجب أن يكون رقمًا موجبًا أو `null` وفق العقد.

**Semantic Validation** يتحقق من معنى البيانات وصحتها في سياق المهمة.

مثال: إذا كان العميل يطلب الشراء، فلا ينبغي أن يُصنّف الطلب على أنه استئجار لمجرد أن النموذج أعاد JSON صالحًا.

قد تنجح النتيجة في اختبار البنية وتفشل في اختبار المعنى؛ لذلك نحتاج إلى كليهما.

# 📚 LAYER 7 — Testing RAG Systems

## 9. RAG Evaluation

في نظام RAG، لا نختبر الإجابة النهائية فقط.

يجب تقييم مراحل متعددة:

1. تجهيز مصادر المعرفة.
2. تقسيم المستندات إلى Chunks.
3. إنشاء Embeddings وفهرستها.
4. استرجاع المقاطع المناسبة.
5. استخدام السياق المسترجع لتوليد الإجابة.
6. عرض الإجابة والمصادر عند الحاجة.

قد تكون الإجابة ضعيفة لأن الاسترجاع فشل، حتى لو كان نموذج التوليد قادرًا على صياغة إجابات جيدة.

### 9.1 Retrieval Quality

نسأل:

- هل استُرجعت المقاطع ذات الصلة بالسؤال؟
- هل فات النظام مصدر مهم؟
- هل المقاطع المسترجعة تحتوي على معلومات كافية؟
- هل تظهر نتائج غير مرتبطة بسبب إعدادات الاسترجاع؟

### 9.2 Groundedness

نسأل:

- هل تدعم المصادر المسترجعة الادعاءات الأساسية في الإجابة؟
- هل أضاف النظام معلومات لا يدعمها السياق؟
- هل يصرّح بعدم كفاية المعلومات عندما تكون المصادر غير كافية؟

وجود مصادر في الإجابة لا يثبت وحده أن الإجابة مستندة إليها فعلًا.

### 9.3 RAG Test Cases

| Test | Expected Behavior |
|---|---|
| سؤال إجابته موجودة بوضوح في قاعدة المعرفة | إجابة صحيحة مدعومة بالمصدر |
| سؤال إجابته موزعة على أكثر من مقطع | استرجاع سياق كافٍ وتجميعه بصورة صحيحة |
| سؤال خارج نطاق قاعدة المعرفة | عدم اختلاق إجابة وكشف حدود المعرفة |
| سؤال غامض | طلب توضيح عند الحاجة |
| سؤال عن معلومة قديمة | تطبيق سياسة تحديث المعرفة أو توضيح حدود المصدر |
| مستند يحتوي على تعليمات غير موثوقة | التعامل معها كمحتوى، لا كتعليمات تتحكم بالنظام |

### 9.4 Measure Retrieval and Answer Quality Separately

عند توفر أدوات التقييم المناسبة، يمكن استخدام مقاييس مثل:

- `Precision@K`: نسبة النتائج المسترجعة ذات الصلة ضمن أول K نتيجة.
- `Recall@K`: مدى استرجاع المقاطع المهمة ضمن أول K نتيجة.
- `Faithfulness`: مدى استناد الإجابة إلى السياق المتاح.
- `Answer Relevance`: مدى ارتباط الإجابة بالسؤال.

تختلف طريقة حساب هذه المقاييس وتعريفاتها بين الأدوات، وقد تحتاج إلى بيانات مرجعية أو تقييم بشري.

لا تعتمدي على رقم واحد لإعلان نجاح RAG؛ يجب النظر إلى جودة الاسترجاع والإجابة معًا.

# 🧠 LAYER 8 — Testing AI Agents

## 10. An Agent Must Be Tested for Actions, Not Just Answers

قد يعطي AI Agent إجابة لغوية ممتازة، لكنه ينفذ إجراءً خاطئًا أو يستخدم أداة غير مناسبة.

لذلك، يجب تقييم:

- هل فهم الهدف؟
- هل اختار الأداة المناسبة؟
- هل مرر البيانات الصحيحة؟
- هل التزم بصلاحياته؟
- هل توقف عندما وصل إلى الهدف؟
- هل تعامل مع فشل الأداة؟
- هل طلب توضيحًا عندما كانت المعلومات غير كافية؟
- هل تجنب تنفيذ إجراءات غير مسموح بها؟

### Example: Lead Qualification Agent

إذا كان الهدف هو تأهيل عميل عقاري، يمكن أن نختبر:

1. عميلًا يقدم معلوماته تدريجيًا.
2. عميلًا يغيّر أحد متطلباته.
3. عميلًا يرفض تقديم معلومة اختيارية.
4. عميلًا يقدم معلومة غير صالحة.
5. فشل أداة حفظ البيانات.
6. طلبًا لتعديل معلومات سبق حفظها.
7. رسالة تطلب من الوكيل تجاوز قيوده.
8. تكرار الرسالة نفسها.

### Tool-Use Evaluation

لا يكفي أن نختبر الرسالة النهائية.

يجب التحقق من:

- اسم الأداة التي استُخدمت.
- المدخلات التي أُرسلت إليها.
- صلاحية العملية.
- النتيجة التي أعادتها الأداة.
- ما إذا كان الوكيل تصرف بناءً على النتيجة الفعلية.

### Agent Reliability Rule

> The agent may decide what to do, but the system must control what it is allowed to do.

قد يختار الوكيل الإجراء، لكن يجب أن يفرض النظام حدود الصلاحيات والتحقق من العمليات الحساسة.

# 🛡️ LAYER 9 — Security and Prompt Injection Testing

## 11. Test Untrusted Inputs

قد تحتوي رسائل المستخدمين أو المستندات أو صفحات الويب على تعليمات تحاول تغيير سلوك AI أو دفعه إلى كشف معلومات أو تنفيذ إجراءات غير مسموحة.

يسمى أحد هذه الأنماط `Prompt Injection`.

### Example

قد يحتوي مستند مسترجع على نص يطلب من AI تجاهل التعليمات السابقة أو كشف بيانات سرية.

يجب تصميم النظام بحيث يتعامل مع هذا النص باعتباره محتوى غير موثوق، لا باعتباره مصدرًا لصلاحيات جديدة.

### What Should We Test?

- محاولة تجاهل تعليمات النظام.
- طلب كشف مفاتيح API.
- محاولة الوصول إلى بيانات مستخدم آخر.
- تعليمات خبيثة داخل مستند مسترجع.
- طلب تنفيذ إجراء خارج نطاق الوكيل.
- مدخلات تحاول تمرير أوامر غير متوقعة إلى الأدوات.

### Security Controls

- تطبيق أقل صلاحية ممكنة `Least Privilege`.
- التحقق من الصلاحيات على الخادم.
- فصل البيانات غير الموثوقة عن التعليمات التشغيلية.
- عدم الاعتماد على Prompt وحده لحماية العمليات الحساسة.
- التحقق من مدخلات الأدوات ومخرجاتها.
- طلب موافقة بشرية عند الحاجة إلى إجراءات حساسة.
- عدم كشف الأسرار في الاستجابات أو Logs.

**مهم:** لا توجد صياغة Prompt تضمن وحدها منع جميع محاولات Prompt Injection. يجب أن تتضمن الحماية ضوابط في تصميم النظام والصلاحيات وتدفق البيانات.

# 🔄 LAYER 10 — Testing Workflow Reliability

## 12. Test What Happens When a Workflow Fails

يجب اختبار المسارات التي لا تسير كما خُطط لها.

في n8n، راجعي كل خطوة مهمة وحددي ما الذي قد يحدث إذا فشلت.

### 12.1 Failure Scenarios

| Scenario | What to Verify |
|---|---|
| Webhook receives invalid input | رفض الطلب بصورة واضحة |
| Database is temporarily unavailable | اكتشاف الفشل والتعامل معه |
| AI Provider times out | عدم إعلان نجاح غير حقيقي |
| AI returns invalid output | منع حفظ البيانات غير الصالحة |
| Save operation fails | عدم اعتبار العملية مكتملة |
| Workflow executes twice | عدم تكرار الأثر غير المقصود |
| External service rate-limits requests | التعامل مع حدود الاستخدام |
| User retries after a timeout | تحديد ما إذا كانت العملية السابقة قد نجحت |
| Workflow stops midway | إمكانية تشخيص الحالة واستعادتها |

### 12.2 Retry Testing

لا تختبري فقط ما إذا كانت إعادة المحاولة تعمل.

اختبري أيضًا ما إذا كانت إعادة المحاولة تسبب تكرارًا.

مثال:

إذا نجح AI في إنشاء خطة، لكن الاتصال انقطع قبل أن يعرف التطبيق أن النتيجة حُفظت، فقد يعيد التطبيق الطلب.

يجب أن يحدد التصميم ما إذا كان عليه:

- استرجاع النتيجة الموجودة.
- متابعة المعالجة السابقة.
- إعادة المحاولة بأمان.
- أو إنشاء نتيجة جديدة إذا كان المستخدم قد طلب ذلك صراحة.

### 12.3 Partial Failure

قد تنجح بعض خطوات Workflow بينما تفشل خطوات أخرى.

مثال:

- تم حفظ الطلب.
- نجح استدعاء AI.
- فشل حفظ الخطة.

يجب أن تكون حالة الطلب واضحة، وألا تعرض الواجهة نجاحًا كاملًا.

وقد يحتاج النظام إلى آلية لاستكمال المعالجة أو إعادة المحاولة دون تكرار الآثار السابقة.

### 12.4 Timeout Testing

اختبري ما يحدث عندما تتأخر الخدمة الخارجية أو لا تستجيب ضمن الزمن المتوقع.

تحققي من:

- ظهور حالة مناسبة للمستخدم.
- تسجيل الخطأ بصورة تساعد على التشخيص.
- عدم تكرار العملية تلقائيًا بصورة غير آمنة.
- إمكانية معرفة ما إذا كانت العملية قد اكتملت بالفعل.
- عدم ترك الطلب في حالة غامضة إلى أجل غير محدد.

# 🔁 LAYER 11 — Idempotency and Data Integrity

## 13. Prevent Duplicate Side Effects

قد يحدث التكرار بسبب:

- ضغط المستخدم على الزر عدة مرات.
- إعادة إرسال طلب بعد Timeout.
- إعادة محاولة تلقائية.
- تشغيل Workflow أكثر من مرة.
- تنفيذ طلبين متزامنين.

### Example

إذا كان كل طلب يجب أن ينتج خطة واحدة، فلا نريد إنشاء ثلاث خطط بسبب تكرار الاستدعاء نفسه.

### What to Test?

1. إرسال الطلب مرة واحدة.
2. إرسال الطلب نفسه مرة ثانية.
3. إعادة المحاولة بعد انقطاع الاتصال.
4. تشغيل طلبين متزامنين للمعرّف نفسه.
5. التحقق من عدد السجلات الناتجة.
6. التحقق من أن الحالة النهائية صحيحة.

### Important Distinction

وجود `UNIQUE constraint` في قاعدة البيانات قد يمنع تكرار السجل، لكنه لا يضمن أن جميع خطوات Workflow أصبحت آمنة من التكرار.

يجب أن يتعامل النظام مع حالة تعارض الحفظ بطريقة صحيحة، وأن يتأكد من عدم تكرار الآثار الخارجية مثل إرسال رسائل أو تنفيذ مدفوعات.

**Idempotency must be designed and tested at the operation level.**

# 📈 LAYER 12 — Performance and Observability

## 14. Performance Testing

اختبري أداء النظام وفق طبيعة الاستخدام المتوقعة.

يمكن قياس:

- زمن استجابة الواجهة.
- زمن استدعاء API.
- زمن تنفيذ Workflow.
- زمن استجابة AI Provider.
- زمن حفظ البيانات واسترجاعها.
- معدل نجاح الطلبات.
- عدد الطلبات التي يمكن للنظام التعامل معها ضمن الحدود المتوقعة.

ليس كل تأخير ناتجًا عن AI؛ قد تكون المشكلة في الشبكة أو قاعدة البيانات أو كثرة الخطوات أو تصميم الاستعلامات.

### 14.1 Define Acceptable Limits

لا تكتفي بعبارة «يجب أن يكون النظام سريعًا».

حددي معيارًا يناسب الاستخدام.

مثال:

- يجب أن تظهر حالة بدء المعالجة للمستخدم سريعًا.
- يجب ألا ينتظر المستخدم اتصالًا مفتوحًا طويلًا إذا كانت المهمة تستغرق وقتًا ملحوظًا.
- يجب أن يتمكن المستخدم من معرفة حالة طلبه.
- يجب أن تكون هناك طريقة واضحة لمعرفة ما إذا كان الطلب قد فشل.

القيم الرقمية الدقيقة يجب أن تُحدد بناءً على متطلبات المشروع والبيئة الفعلية، ثم تُختبر بقياسات حقيقية.

---

## 15. Observability: Logs, Status, and Metrics

`Observability` تعني القدرة على فهم ما يحدث داخل النظام من خلال المعلومات التي ينتجها أثناء التشغيل.

في الأنظمة المتكاملة، لا يكفي أن نعرف أن الطلب فشل؛ نحتاج إلى معرفة أين فشل ولماذا.

### 15.1 Logs

يمكن أن تسجل المعلومات التشغيلية الضرورية، مثل:

- وقت بدء التنفيذ وانتهائه.
- معرّف الطلب.
- المرحلة التي وصل إليها التنفيذ.
- حالة العملية.
- نوع الخطأ.
- زمن التنفيذ.

يجب تجنب تسجيل كلمات المرور ومفاتيح API والبيانات الشخصية الحساسة أو محتوى المستخدم كاملًا دون حاجة واضحة وضوابط مناسبة.

### 15.2 Correlation ID

هو معرّف يساعد على ربط الأحداث المرتبطة بالعملية نفسها عبر مكونات النظام.

مثال:

```text
request_id: req_1042

Frontend:
Request submitted

Server-Side Function:
Webhook called

n8n:
Workflow started

AI:
Generation completed

Supabase:
Plan saved

Frontend:
Result retrieved
```

يمكن استخدام `request_id` لهذا الغرض إذا كان مناسبًا، أو إنشاء معرّف تتبع منفصل.

لكن يجب التمييز بين:

- `request_id`: معرّف الطلب التجاري أو سجل البيانات.
- `correlation_id`: معرّف تتبع يساعد على ربط الأحداث التقنية.

قد يكونان متطابقين في تصميم بسيط، لكنهما ليسا المفهوم نفسه بالضرورة.

### 15.3 Metrics

من المفيد متابعة:

- نسبة الطلبات الناجحة.
- نسبة الطلبات الفاشلة.
- متوسط زمن المعالجة.
- عدد حالات Timeout.
- عدد محاولات إعادة التنفيذ.
- عدد الطلبات التي بقيت في حالة `processing` مدة غير طبيعية.
- جودة مخرجات AI وفق مجموعة الاختبار.

### 15.4 Status Transitions

يجب تحديد انتقالات الحالة المسموح بها.

مثال:

```text
pending
   |
   v
processing
   |
   +------> completed
   |
   +------> failed
```

إذا أعيدت المحاولة، يجب أن يحدد التصميم كيف تتغير الحالة وما المعلومات التي تُحفظ عن المحاولات السابقة.

وجود حالات واضحة يساعد على اكتشاف الطلبات العالقة، لكنه لا يغني عن وجود آلية للتعامل معها.

# 🔄 LAYER 13 — Regression Testing

## 16. Test Again After Every Important Change

قد يؤدي تعديل صغير إلى كسر وظيفة كانت تعمل سابقًا.

مثال:

- تعديل Prompt قد يحسن الملخصات لكنه يجعل استخراج الأرقام أقل دقة.
- تغيير Model قد يؤثر في جودة النتائج.
- تغيير Schema قد يتسبب في فشل حفظ البيانات.
- تعديل RAG Chunk Size قد يحسن استرجاع بعض الأسئلة ويضعف أسئلة أخرى.
- تغيير Workflow قد يؤدي إلى تحديث حالة الطلب قبل حفظ النتيجة.

لذلك نستخدم `Regression Testing`.

### Regression Test Process

1. احتفظي بمجموعة اختبارات معروفة.
2. سجلي النتائج الحالية.
3. غيّري Prompt أو Model أو Workflow.
4. أعيدي تشغيل الاختبارات.
5. قارني النتائج الجديدة بالقديمة.
6. حددي التحسن والتراجع.
7. لا تعتمدي التعديل قبل مراجعة التأثيرات المهمة.

### Versioning

عند الإمكان، سجلي:

- نسخة Prompt.
- اسم Model وإصداره عند توفره.
- إعدادات التوليد المهمة.
- نسخة Workflow.
- نسخة Schema.
- نسخة مجموعة الاختبار.
- نتائج التقييم.

قد تتغير نتائج AI بسبب تحديثات المزود حتى دون تغيير Prompt، لذلك من المهم إعادة التقييم دوريًا وفي الظروف التي تهم المشروع.

# 🧾 LAYER 14 — Bug Reporting

## 17. Document Bugs So They Can Be Reproduced

عندما نكتشف مشكلة، لا نكتب فقط: «النظام لا يعمل».

نكتب تقريرًا يوضح كيف نعيد المشكلة، وما النتيجة المتوقعة، وما حدث بالفعل.

### Bug Report Template

```markdown
# Bug Report

## 1. Summary
Short description of the issue.

## 2. Environment
- Application Version:
- Workflow Version:
- Environment: Development / Staging / Production
- Relevant Configuration:

## 3. Preconditions
What must be true before reproducing the bug?

## 4. Steps to Reproduce
1.
2.
3.

## 5. Expected Result
What should happen?

## 6. Actual Result
What happened instead?

## 7. Severity
Critical / High / Medium / Low

## 8. Priority
P1 / P2 / P3 / P4

## 9. Evidence
Relevant logs, execution references, screenshots,
or test results.

## 10. Suspected Cause
Optional initial hypothesis.

## 11. Fix and Retest
What was changed?
Did the original test pass after the fix?
Did regression tests pass?
```

### Severity vs. Priority

**Severity** تصف مدى تأثير المشكلة على النظام أو المستخدم.

**Priority** تحدد مدى استعجال إصلاحها ضمن خطة العمل.

قد تكون المشكلة عالية التأثير وعالية الأولوية، لكنهما ليسا مترادفين دائمًا.

مثال:

- كشف بيانات مستخدم آخر: غالبًا `Critical` أو `High` حسب السياق، ويحتاج إلى معالجة عاجلة.
- خطأ إملائي في عنوان صفحة غير أساسية: غالبًا منخفض التأثير والأولوية.

يجب تقييم كل حالة وفق أثرها الفعلي، لا وفق اسمها فقط.

# 🛠️ LAYER 16 — Practical Exercise

## Exercise: Prove Your Solution Works

اختاري مشروعًا من المشاريع التي بنيتِها، مثل:

- PlanCraft AI.
- Real Estate Lead Qualification Agent.
- TECHFIX RAG Assistant.
- AI Client Intake and Request Routing.

المطلوب هو إعداد خطة اختبار مناسبة للمشروع وتنفيذها، ثم توثيق النتائج.

### Task 1 — Define Acceptance Criteria

اكتبي من 5 إلى 10 معايير قبول واضحة.

مثال PlanCraft AI:

- يستطيع المستخدم إرسال طلب صحيح.
- يُحفظ الطلب في قاعدة البيانات.
- تتم معالجة الطلب وفق الحالة المحددة.
- تُفحص مخرجات AI قبل حفظها.
- تُحفظ الخطة المرتبطة بالطلب الصحيح.
- يستطيع المستخدم استرجاع الخطة.
- لا تظهر نتيجة مكتملة إذا فشلت عملية الحفظ.
- لا يؤدي تكرار الطلب إلى إنشاء أثر مكرر غير مقصود.

### Task 2 — Build a Test Matrix

أنشئي ما لا يقل عن 10 حالات اختبار، تشمل:

- حالات نجاح.
- مدخلات غير صحيحة.
- حقولًا ناقصة.
- فشلًا في إحدى الخدمات.
- مخرجات AI غير صالحة.
- تكرار الطلب.
- التحقق من الصلاحيات.
- التحقق من حفظ البيانات واسترجاعها.
- حالة لا تكفي فيها المعلومات لإنتاج إجابة موثوقة.
- حالة تستدعي إعادة الاختبار بعد الإصلاح.

اختاري الحالات التي تناسب المشروع فعلًا، وأضيفي حالات أخرى إذا تطلبت المخاطر ذلك.

### Task 3 — Execute the Tests

نفّذي الاختبارات وسجلي:

- المدخلات.
- الخطوات.
- النتيجة المتوقعة.
- النتيجة الفعلية.
- PASS أو FAIL أو BLOCKED.
- الدليل.

### Task 4 — Evaluate AI Quality

إذا كان المشروع يستخدم AI، جهّزي مجموعة أمثلة تمثل الاستخدام المتوقع.

قيّمي:

- الدقة.
- اكتمال البيانات.
- الالتزام بالتعليمات.
- التعامل مع المعلومات الناقصة.
- مقاومة اختلاق المعلومات.
- صحة البنية عند استخدام Structured Output.

إذا كان المشروع يستخدم RAG أو Agent، أضيفي اختبارات خاصة بالاسترجاع أو استخدام الأدوات.

### Task 5 — Fix and Retest

اختاري مشكلة واحدة على الأقل اكتشفتِها.

1. وثّقي المشكلة.
2. حددي سببها المحتمل.
3. نفّذي الإصلاح.
4. أعيدي الاختبار الأصلي.
5. أعيدي اختبارات أخرى قد تتأثر بالإصلاح.
6. وثّقي النتيجة.

### Deliverables

- Acceptance Criteria.
- Test Matrix.
- AI Evaluation Dataset عند الحاجة.
- Test Report.
- Bug Report لمشكلة واحدة على الأقل، إذا اكتشفتِ مشكلة قابلة للتوثيق.
- دليل على إعادة الاختبار بعد الإصلاح.
- قائمة بالمخاطر أو القيود التي ما زالت قائمة.

# ✅ Definition of Done

تكون مرحلة Testing and Reliability مكتملة عندما:

- [ ] توجد معايير قبول واضحة.
- [ ] تم اختبار المتطلبات الأساسية.
- [ ] تم اختبار المسار الكامل من البداية إلى النهاية.
- [ ] تم اختبار المدخلات غير الصحيحة والحالات الحدّية المهمة.
- [ ] تم اختبار تكامل المكونات.
- [ ] تم التحقق من صحة حفظ البيانات واسترجاعها.
- [ ] تم اختبار حالات الفشل وإعادة المحاولة والتكرار عند انطباقها.
- [ ] تم اختبار صلاحيات الوصول المناسبة.
- [ ] تم تقييم جودة مخرجات AI وفق معايير واضحة.
- [ ] تم اختبار RAG أو Agent عند استخدامهما.
- [ ] تم توثيق الأخطاء والقيود المعروفة.
- [ ] أُعيدت الاختبارات المناسبة بعد الإصلاح.
- [ ] يوجد تقرير يوضح النتائج الفعلية.
- [ ] لا توجد مشكلة حرجة معروفة تمنع الانتقال إلى المرحلة التالية.

اجتياز هذه القائمة لا يضمن خلو النظام من جميع الأخطاء؛ لكنه يوفر دليلًا منظمًا على مستوى الجودة الذي تم اختباره.

# 🧠 Final Engineering Mindset

لا تسألي فقط:

- هل اشتغل التطبيق؟
- هل أعاد AI إجابة؟
- هل نجح الـ Workflow؟
- هل اختفت رسالة الخطأ؟

بل اسألي:

- هل تحقق المتطلب فعلًا؟
- هل النتيجة صحيحة ومناسبة للمستخدم؟
- هل يستطيع النظام اكتشاف المدخلات غير الصحيحة؟
- هل يتعامل مع فشل الخدمات دون ادعاء النجاح؟
- هل يمكن تكرار الطلب دون آثار غير مقصودة؟
- هل يمكن تتبع المشكلة عند حدوثها؟
- هل نمتلك دليلًا على جودة النتائج؟
- هل نعرف القيود التي ما زالت موجودة؟

**Testing provides evidence. Reliability comes from designing for failure, controlling risk, and learning from real results.**
