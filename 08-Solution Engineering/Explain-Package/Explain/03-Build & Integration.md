# 🏗️ U8 — Build and Integration
## From Designed Architecture to a Working Integrated System

---

## 🎯 1. Learning Objectives

في هذا الجزء، سنتعلم كيف نحوّل التصميم الهندسي للحل إلى نظام يعمل فعليًا، من خلال بناء المكونات وربطها واختبار انتقال البيانات بينها.

بنهاية هذا الجزء، يجب أن نكون قادرين على:

- تحويل `Solution Design` إلى خطة تنفيذ واضحة.
- تحديد ترتيب بناء المكونات والاعتماديات بينها.
- بناء قاعدة البيانات باستخدام Supabase.
- بناء واجهة التطبيق باستخدام Lovable.
- بناء AI Workflow باستخدام n8n.
- فهم دور `Server-Side Functions` في ربط التطبيق بالخدمات الخارجية.
- تصميم `API Contracts` و`Data Contracts`.
- ربط المكونات باستخدام APIs وWebhooks.
- التعامل مع الأخطاء والطلبات المتكررة.
- اختبار التكامل بين المكونات وتشخيص مشكلاته.
- التأكد من أن البيانات تنتقل وتُحفظ بالشكل الصحيح.

### Engineering Principle

> A working component is not the same as a working system.

نجاح كل أداة بمفردها لا يعني أن الحل المتكامل يعمل.

قد تعمل واجهة التطبيق بصورة صحيحة، وقد يستقبل n8n الطلبات بنجاح، وقد تكون قاعدة البيانات سليمة، لكن النظام كله يفشل إذا لم تنتقل البيانات بينها بالشكل الصحيح.

هدفنا ليس بناء مكونات تعمل منفصلة، بل بناء **نظام متكامل يمكن الاعتماد عليه**.

# 🧩 LAYER 1 — Implementation Planning

## 2. From Architecture to Implementation

بعد الانتهاء من `Requirements and Solution Design`، يجب أن نعرف:

- ما المشكلة التي نحلها؟
- ما المتطلبات التي يجب تحقيقها؟
- ما المكونات التي نحتاج إليها؟
- كيف ستتواصل هذه المكونات؟
- ما البيانات التي ستنتقل بينها؟

الخطوة التالية هي تحويل التصميم إلى خطة تنفيذ.

### Implementation Plan

هي خطة توضّح:

- ما الذي سنبنيه؟
- بأي ترتيب؟
- ما المكونات التي تعتمد على مكونات أخرى؟
- كيف سنتحقق من نجاح كل مرحلة؟

### مثال: PlanCraft AI

نريد بناء تطبيق يستقبل طلب المستخدم، ثم يستخدم AI لإنشاء خطة مشروع ويحفظ النتيجة في قاعدة البيانات.

يمكن تقسيم التنفيذ إلى:

1. إنشاء جداول قاعدة البيانات.
2. التحقق من صلاحيات الوصول إلى البيانات.
3. بناء واجهة إرسال الطلب.
4. حفظ الطلب في قاعدة البيانات.
5. بناء Workflow في n8n لمعالجة الطلب.
6. ربط Workflow بمزود AI.
7. التحقق من مخرجات AI.
8. حفظ الخطة الناتجة.
9. ربط التطبيق بـ n8n.
10. عرض الخطة الحقيقية للمستخدم.
11. اختبار مسار النجاح والفشل.

هذا الترتيب يقلل احتمال بناء واجهة تعتمد على بيانات أو وظائف لم تُنفّذ بعد.

### Engineering Principle

> Build in dependency order, not in tool order.

لا نبني النظام وفق ترتيب الأدوات التي نحب استخدامها، بل وفق الاعتماديات التي يحتاج إليها النظام.

# 🗄️ LAYER 2 — Database Implementation

## 3. Build the Data Foundation

قاعدة البيانات ليست مجرد مكان نخزن فيه المعلومات؛ إنها جزء من تصميم النظام ومسؤولة عن الحفاظ على سلامة البيانات واتساقها.

في هذا المشروع، يمكن استخدام **Supabase** لتوفير PostgreSQL Database وخدمات مرتبطة بها.

قبل بناء الواجهة أو الـ Workflow، يجب تحويل `Data Model` إلى بنية فعلية.

### مثال

في PlanCraft AI، نحتاج إلى جدولين:

**`project_requests`**

يخزّن الطلبات التي يرسلها المستخدم.

حقول محتملة:

- `id`
- `title`
- `description`
- `goal`
- `additional_context`
- `status`
- `created_at`
- `updated_at`

**`project_plans`**

يخزّن الخطط التي ينتجها النظام.

حقول محتملة:

- `id`
- `request_id`
- `summary`
- `project_goal`
- `phases`
- `recommended_actions`
- `risks`
- `estimated_duration`
- `created_at`

قد تكون بعض الحقول من نوع `JSONB` عندما نحتاج إلى تخزين بيانات منظمة ذات بنية متغيرة، مثل مراحل المشروع أو قائمة المخاطر.

لكن اختيار نوع البيانات يجب أن يعتمد على طريقة استخدام المعلومات، وليس على سهولة التخزين فقط.

## 3.1 Database Constraints

يجب ألا نعتمد على الواجهة وحدها لمنع البيانات غير الصحيحة.

يمكن استخدام:

- `NOT NULL` للحقول المطلوبة.
- `FOREIGN KEY` لربط الجداول.
- `UNIQUE` لمنع تكرار قيمة يجب أن تكون فريدة.
- `CHECK` للتحقق من شروط محددة.
- `DEFAULT` لتحديد قيمة افتراضية.

مثلاً، إذا كان لكل طلب خطة واحدة فقط، فيمكن استخدام `UNIQUE` على `request_id` في جدول الخطط.

هذا يمنع إنشاء أكثر من سجل خطة للطلب نفسه، لكنه لا يكفي وحده لضمان أن معالجة الطلب آمنة من التكرار؛ يجب أيضًا تصميم منطق الـ Workflow بصورة صحيحة.

## 3.2 Row Level Security — RLS

عندما يحتوي التطبيق على بيانات مستخدمين، يجب تحديد من يستطيع قراءة كل سجل أو إنشاؤه أو تعديله أو حذفه.

توفر Supabase آلية `Row Level Security (RLS)` لتطبيق سياسات الوصول على مستوى الصفوف.

يجب أن نسأل:

- هل يستطيع المستخدم قراءة بيانات مستخدم آخر؟
- هل يمكنه تعديل سجل لا يملكه؟
- هل يمكن إرسال طلبات مباشرة إلى قاعدة البيانات لتجاوز الواجهة؟
- هل تحتاج بعض العمليات إلى تنفيذ آمن على الخادم؟

**مهم:** إخفاء زر أو صفحة في الواجهة لا يُعد حماية كافية للبيانات.

كذلك، لا يجوز وضع مفاتيح الخدمة الحساسة، مثل `service_role key`، داخل كود الواجهة الأمامية.

### Checkpoint

قبل الانتقال إلى المرحلة التالية، تأكد من:

- إنشاء الجداول والحقول المطلوبة.
- تعريف العلاقات والقيود.
- تحديد قيم الحالات `status` بصورة واضحة.
- تطبيق سياسات الوصول المناسبة.
- اختبار عمليات القراءة والكتابة المسموح بها والممنوعة.
- التأكد من أن بنية قاعدة البيانات تدعم المتطلبات الفعلية.

# 🖥️ LAYER 3 — Application Development

## 4. Build the User Interface

بعد تجهيز أساس البيانات، نبني الواجهة التي يتفاعل معها المستخدم.

يمكن استخدام **Lovable** لتسريع بناء واجهة التطبيق ومنطقها، مع ضرورة مراجعة التنفيذ واختباره بدل افتراض أن كل ما تولّده الأداة صحيح.

### 4.1 Start with the User Journey

قبل طلب بناء الصفحات، حدّد رحلة المستخدم.

مثال PlanCraft AI:

1. يفتح المستخدم التطبيق.
2. يدخل عنوان المشروع ووصفه.
3. يحدد الهدف والسياق الإضافي عند الحاجة.
4. يضغط زر إنشاء الخطة.
5. يحفظ التطبيق الطلب.
6. يبدأ النظام المعالجة.
7. تظهر حالة الطلب للمستخدم.
8. عند اكتمال المعالجة، تظهر الخطة المحفوظة.
9. يستطيع المستخدم فتح خططه السابقة.

هذه الرحلة تحدد الصفحات والحالات التي يجب تنفيذها.

### 4.2 Design UI States

لا تصمم الواجهة لحالة النجاح فقط.

يجب التفكير في الحالات التالية:

| UI State | المعنى |
|---|---|
| `Idle` | المستخدم لم يرسل الطلب بعد |
| `Validating` | التحقق من المدخلات |
| `Submitting` | إرسال الطلب |
| `Processing` | الطلب قيد المعالجة |
| `Success` | النتيجة جاهزة |
| `Empty` | لا توجد نتائج بعد |
| `Error` | حدث خطأ |
| `Retry Available` | يمكن إعادة المحاولة |

إذا كانت المعالجة تستغرق وقتًا، فلا تجعل المستخدم يظن أن التطبيق توقف عن العمل.

اعرض حالة واضحة، واستخدم آلية مناسبة لتحديث النتيجة.

### 4.3 Separate UI from Business Logic

يجب أن تكون مسؤوليات المكونات واضحة.

**Frontend:**
- عرض البيانات.
- استقبال مدخلات المستخدم.
- التحقق الأولي من الحقول.
- إظهار حالات التحميل والنجاح والفشل.
- إرسال الطلب إلى نقطة الاتصال المناسبة.

**Backend / Server-Side Logic:**
- تنفيذ العمليات التي تحتاج إلى صلاحيات آمنة.
- التحقق من هوية المستخدم وصلاحياته عند الحاجة.
- استدعاء الخدمات الخارجية.
- التعامل مع الأسرار.
- فرض قواعد العمل التي لا يجوز الاعتماد على الواجهة وحدها لحمايتها.

**Database:**
- حفظ البيانات.
- فرض القيود.
- إدارة العلاقات.
- تطبيق سياسات الوصول.

لا يعني ذلك أن كل تطبيق يحتاج إلى Backend مستقل؛ بل يجب اختيار مكان تنفيذ كل مسؤولية وفق متطلبات الأمان والبنية.

### مثال على طلب بناء الواجهة

يمكن أن نطلب من Lovable:

- بناء نموذج لإرسال طلب مشروع.
- حفظ الطلب في جدول `project_requests`.
- عرض قائمة الطلبات المحفوظة.
- عرض حالة كل طلب.
- فتح صفحة تفاصيل الطلب والخطة الناتجة.
- إظهار حالات التحميل والنجاح والفشل.
- عدم إنشاء نتائج AI وهمية.
- عدم عرض خطة على أنها مكتملة ما لم تكن محفوظة فعلًا في قاعدة البيانات.

بعد التوليد، يجب فحص الكود والسلوك الفعلي واختبار مسار المستخدم.

# ⚙️ LAYER 4 — Workflow Engineering

## 5. Build the Automation Workflow

بعد تحديد وظيفة الـ Workflow في التصميم، نبنيه باستخدام **n8n** أو الأداة المناسبة.

يجب أن يكون لكل Workflow هدف واضح ومدخلات ومخرجات محددة.

### 5.1 Define the Workflow Contract

قبل إضافة Nodes، أجب عن الأسئلة التالية:

- ما الذي يبدأ التنفيذ؟
- ما البيانات التي تصل إلى Workflow؟
- كيف نتحقق من صحة البيانات؟
- ما مصادر البيانات التي يحتاج إليها؟
- أين يُستخدم AI؟
- كيف نتحقق من مخرجات AI؟
- أين تُحفظ النتيجة؟
- ما الذي يحدث إذا فشلت خطوة؟
- ما الاستجابة التي يتلقاها النظام المستدعي؟

### 5.2 Example: PlanCraft AI Workflow

يمكن أن يتكون المسار من الخطوات التالية:

1. **Webhook:** استقبال طلب إنشاء الخطة.
2. **Input Validation:** التحقق من وجود `request_id` وصحة شكله.
3. **Load Request:** قراءة الطلب من Supabase.
4. **Check Request Status:** التحقق من حالة الطلب وما إذا كانت هناك معالجة سابقة.
5. **AI Generation:** إرسال المعلومات إلى نموذج AI لإنشاء الخطة.
6. **Output Validation:** التحقق من بنية النتيجة واكتمال الحقول المطلوبة.
7. **Save Project Plan:** حفظ الخطة في قاعدة البيانات.
8. **Update Request Status:** تحديث حالة الطلب.
9. **Respond to Webhook:** إرجاع استجابة واضحة للجهة التي استدعت الـ Workflow.

قد تختلف العقد أو تتوزع الخطوات على أكثر من Workflow بحسب تعقيد النظام، لكن المسؤوليات الأساسية يجب أن تكون موجودة.

### 5.3 Validate AI Output

لا تفترض أن نموذج AI سيعيد دائمًا بيانات صحيحة لمجرد أنك طلبت منه الالتزام بصيغة معينة.

يجب التحقق من:

- وجود الحقول المطلوبة.
- مطابقة الأنواع المتوقعة.
- كون المصفوفات والكائنات بالصيغة الصحيحة.
- عدم فقدان معلومات أساسية.
- توافق النتيجة مع قواعد العمل.
- عدم تمرير نتيجة غير صالحة إلى قاعدة البيانات.

يمكن استخدام `Structured Output Parser` أو `JSON Schema` للمساعدة في ضبط البنية، لكن يظل التحقق الفعلي من البيانات ضروريًا.

### مثال

إذا كان النظام يتوقع:

```json
{
  "summary": "A short project summary",
  "project_goal": "The main objective",
  "phases": [
    {
      "title": "Research",
      "objective": "Understand the problem",
      "actions": [
        "Interview users",
        "Review alternatives"
      ],
      "priority": "high"
    }
  ],
  "recommended_actions": [
    "Validate the requirements"
  ],
  "risks": [
    {
      "risk": "Unclear scope",
      "mitigation": "Define acceptance criteria"
    }
  ],
  "estimated_duration": "4 weeks"
}
```

فيجب التحقق من أن `phases` مصفوفة، وأن كل مرحلة تحتوي على الحقول المطلوبة، وأن `priority` من القيم المسموح بها إذا كان النظام يحدد مجموعة ثابتة منها.

**Structured output helps with format; validation protects the system.**

# 🔐 LAYER 5 — Server-Side Functions

## 6. Understand the Server-Side Role

قد يحتاج التطبيق إلى استدعاء خدمة خارجية أو Workflow مع الاحتفاظ بالمفاتيح السرية بعيدًا عن المتصفح.

هنا يأتي دور `Server-Side Function`.

هي وظيفة تعمل في بيئة خادم بدلًا من تشغيلها مباشرة في متصفح المستخدم.

يمكن أن تنفّذ وظائف مثل:

- التحقق من الطلب.
- التحقق من صلاحيات المستخدم.
- استدعاء Webhook في n8n.
- تمرير البيانات المطلوبة.
- معالجة الاستجابة.
- تسجيل الأخطاء.
- إعادة نتيجة مناسبة إلى الواجهة.

### Example Flow

```text
User
  |
  v
Frontend
  |
  v
Server-Side Function
  |
  v
n8n Webhook
  |
  v
AI Processing
  |
  v
Supabase
```

هذا مثال على أحد التصاميم الممكنة، وليس شرطًا أن تمر كل عملية قراءة أو كتابة في قاعدة البيانات عبر Server-Side Function.

يعتمد المسار الصحيح على الصلاحيات، وطبيعة العملية، وطريقة الاتصال المعتمدة.

## 6.1 Why Not Call Everything from the Frontend?

إذا وضعنا مفتاح API سريًا داخل كود الواجهة، فقد يتمكن المستخدم من اكتشافه من خلال أدوات المتصفح أو الملفات المحمّلة.

لذلك، يجب الاحتفاظ بالأسرار في بيئة الخادم أو مخزن الأسرار المناسب.

لكن وجود Server-Side Function لا يجعل العملية آمنة تلقائيًا. يجب أيضًا التحقق من:

- هوية المستخدم عند الحاجة.
- الصلاحيات المطلوبة.
- المدخلات القادمة من العميل.
- الوجهات التي يسمح للخادم باستدعائها.
- عدم كشف الأسرار في الاستجابات أو السجلات.
- حدود الاستخدام ومعدلات الطلبات.

### Security Principle

> Never trust client input merely because it came from your own application.

يجب التعامل مع بيانات العميل على أنها مدخلات تحتاج إلى التحقق، حتى لو أرسلها تطبيقنا نفسه.

# 🔗 LAYER 6 — API and Webhook Integration

## 7. Connect the Components

الـ API والـ Webhook من الوسائل التي تسمح للمكونات بالتواصل.

### API

واجهة تتيح لنظام أن يطلب بيانات أو ينفذ عملية في نظام آخر وفق عقد محدد.

### Webhook

نقطة استقبال HTTP يمكن أن تستقبل طلبًا عند حدوث حدث أو عند استدعائها من نظام آخر.

في n8n، يمكن استخدام Webhook Trigger لبدء Workflow عند وصول طلب مناسب.

### Example

يستقبل n8n طلبًا يحتوي على:

```json
{
  "request_id": "8f4b6a12-3d27-4e91-8a65-12c4a9d7e201"
}
```

يستخدم Workflow هذا المعرّف للوصول إلى الطلب المحفوظ في قاعدة البيانات.

في هذا التصميم، لا يحتاج التطبيق إلى إرسال كل تفاصيل المشروع مرة أخرى إذا كانت البيانات المطلوبة محفوظة بالفعل في Supabase.

هذا يقلل تكرار البيانات ويجعل قاعدة البيانات مصدرًا واضحًا للطلب الأصلي.

### 7.1 Test Webhook Correctly

عند اختبار Webhook، انتبه إلى:

- استخدام HTTP Method الصحيح، مثل `POST`.
- استخدام عنوان الاختبار أو الإنتاج الصحيح.
- تفعيل الـ Workflow عند الحاجة.
- إرسال `Content-Type: application/json`.
- إرسال البيانات بالشكل المتوقع.
- التحقق من الاستجابة.
- مراجعة سجل التنفيذ في n8n.
- التحقق من الأثر الفعلي في قاعدة البيانات.

قد يفشل Webhook إذا أُرسل إليه `GET` بينما يتوقع `POST`، أو إذا كان عنوان الاختبار غير نشط، أو إذا كان Workflow غير منشور أو غير مفعّل بحسب إعداداته.

### 7.2 Test URL vs Production URL

قد يوفر n8n عنوانًا للاختبار وآخر للإنتاج.

- **Test URL:** يُستخدم عادةً أثناء تطوير Workflow واختباره وفق طريقة تشغيل الاختبار في n8n.
- **Production URL:** يُستخدم عند استدعاء Workflow المفعّل من التطبيق الفعلي.

لا تفترض أن عنوان الاختبار سيعمل بالطريقة نفسها بعد إغلاق جلسة الاختبار.

قبل الربط النهائي، تحقق من أن التطبيق يستخدم العنوان الصحيح وأن الـ Workflow يعمل في وضعه الفعلي.

# 📦 LAYER 7 — Data Contracts

## 8. Define What Each Component Expects

`Data Contract` هو اتفاق واضح يحدد شكل البيانات التي يتوقعها أحد المكونات ويستقبلها أو يعيدها.

يشمل عادةً:

- أسماء الحقول.
- أنواع البيانات.
- الحقول المطلوبة والاختيارية.
- القيم المسموح بها.
- قواعد التحقق.
- شكل الاستجابة.
- طريقة تمثيل الأخطاء.

### Example: Request Contract

```json
{
  "request_id": "uuid"
}
```

هذا العقد يعني أن الجهة المستقبلة تتوقع معرّف الطلب، وليس كائن المشروع الكامل.

### Example: Success Response

```json
{
  "success": true,
  "request_id": "8f4b6a12-3d27-4e91-8a65-12c4a9d7e201",
  "status": "completed"
}
```

### Example: Error Response

```json
{
  "success": false,
  "request_id": "8f4b6a12-3d27-4e91-8a65-12c4a9d7e201",
  "error": {
    "code": "REQUEST_NOT_FOUND",
    "message": "The requested project was not found."
  }
}
```

هذه أمثلة توضيحية؛ يجب تحديد العقد النهائي وفق طريقة عمل التطبيق.

## 8.1 Why Does This Matter?

لنفترض أن الواجهة ترسل:

```json
{
  "requestId": "123"
}
```

بينما يتوقع n8n:

```json
{
  "request_id": "123"
}
```

قد يفشل Workflow لأن اسم الحقل مختلف، رغم أن المعرّف نفسه صحيح.

لذلك، يجب توحيد أسماء الحقول بين:

- Frontend.
- Server-Side Function.
- Webhook.
- Workflow Nodes.
- Database.
- Response.

ولا يكفي أن نتفق على أسماء الحقول فقط؛ يجب أيضًا أن نتفق على أنواعها ومعانيها وقيمها.

### Engineering Principle

> Integration failures often happen at the boundaries between components.

كلما كانت الحدود والعقود أوضح، أصبح الربط أسهل في البناء والاختبار والصيانة.

# 🔄 LAYER 8 — Integration Patterns

## 9. Synchronous vs Asynchronous Processing

يجب أن نحدد كيف سينتظر التطبيق نتيجة العملية.

### 9.1 Synchronous Pattern

يرسل التطبيق طلبًا، وينتظر حتى تعود النتيجة ضمن الاتصال نفسه.

```text
Frontend
   |
   v
Server-Side Function
   |
   v
n8n Workflow
   |
   v
Result
   |
   v
Frontend
```

قد يناسب العمليات القصيرة التي يمكن إتمامها ضمن حدود الوقت المسموح بها للاتصال.

**المخاطر:**
- قد تستغرق العملية وقتًا أطول من المتوقع.
- قد ينتهي الاتصال قبل اكتمال المعالجة.
- قد تتسبب مهلات الانتظار في ظهور فشل رغم أن العملية بدأت بالفعل.

### 9.2 Asynchronous Pattern

يُحفظ الطلب أولًا، ثم تتم معالجته بصورة منفصلة.

```text
1. User submits request
          |
          v
2. Save request in database
          |
          v
3. Return request ID
          |
          v
4. Process request in background
          |
          v
5. Save result and update status
          |
          v
6. Frontend retrieves the result
```

هذا النمط مناسب للعمليات التي قد تستغرق وقتًا أطول، مثل إنشاء خطط باستخدام AI أو تحليل مستندات كبيرة.

### 9.3 Example: PlanCraft AI

يمكن تنفيذ العملية بهذه الطريقة:

1. يرسل المستخدم طلبًا.
2. تحفظ الواجهة الطلب في `project_requests`.
3. يحصل التطبيق على `request_id`.
4. يستدعي التطبيق Server-Side Function لبدء المعالجة في n8n.
5. يعالج n8n الطلب.
6. يحفظ النتيجة في `project_plans`.
7. يحدّث حالة الطلب إلى `completed`.
8. يسترجع التطبيق الخطة المحفوظة ويعرضها.

إذا كانت المعالجة غير متزامنة، فلا ينبغي للواجهة افتراض أن النتيجة جاهزة بمجرد نجاح استدعاء Webhook.

نجاح استدعاء Webhook قد يعني فقط أن الطلب وصل أو أن المعالجة بدأت، وليس بالضرورة أن الخطة أُنشئت وحُفظت.

لذلك يجب أن يعتمد التطبيق على حالة واضحة أو آلية متابعة مناسبة حتى تكتمل العملية.

# 🛡️ LAYER 9 — Reliability During Integration

## 10. Handle Duplicate Requests

قد يضغط المستخدم على الزر مرتين، أو يعيد المتصفح إرسال الطلب، أو يحاول التطبيق تكرار الاستدعاء بعد انتهاء مهلة الاتصال.

إذا لم نصمم النظام للتعامل مع التكرار، فقد ينشئ خططًا متعددة أو ينفذ العملية نفسها أكثر من مرة.

### Idempotency

تعني أن تكرار تنفيذ العملية بنفس المفتاح أو معرّف العملية لا يؤدي إلى تكرار الأثر الذي يفترض أن يحدث مرة واحدة.

في PlanCraft AI، يمكن استخدام `request_id` لتحديد الطلب الأصلي، مع تصميم منطق يمنع إنشاء سجلات خطط مكررة له.

لكن استخدام `request_id` وحده لا يضمن `Idempotency`؛ يجب أن تدعمه قيود قاعدة البيانات ومنطق المعالجة والتعامل مع حالات التنفيذ المتزامن.

### Possible Controls

- منع إرسال الطلب عدة مرات من الواجهة دون حاجة.
- التحقق من حالة الطلب قبل بدء المعالجة.
- استخدام قيود مناسبة في قاعدة البيانات.
- استخدام `UPSERT` أو عملية تحديث مناسبة عند الحاجة.
- التعامل مع الطلبات المتزامنة.
- عدم إنشاء نتيجة جديدة إذا كانت النتيجة المطلوبة مكتملة بالفعل، إلا إذا كانت إعادة التوليد مقصودة.

---

## 11. Handle Failures Explicitly

لا بد أن نحدد ماذا يحدث إذا فشلت خطوة في منتصف Workflow.

مثال:

1. وصل الطلب.
2. قرأ n8n بيانات المشروع.
3. نجح استدعاء AI.
4. فشل حفظ النتيجة في Supabase.

في هذه الحالة، لا يصح أن يعرض التطبيق الخطة على أنها مكتملة إذا لم تُحفظ بصورة يمكن استرجاعها.

يجب أن تكون حالات النظام واضحة، مثل:

- `pending`
- `processing`
- `completed`
- `failed`

ويمكن إضافة حالات أخرى إذا كانت لها دلالة واضحة في التصميم.

### Error Handling Strategy

لكل خطوة مهمة، حدّد:

- ما الأخطاء المحتملة؟
- كيف نكتشفها؟
- هل يمكن إعادة المحاولة؟
- هل يمكن أن تؤدي إعادة المحاولة إلى تكرار الأثر؟
- هل يجب تحديث حالة الطلب؟
- ما الرسالة المناسبة للمستخدم؟
- ما المعلومات التي يجب تسجيلها للتشخيص؟

### Retries

إعادة المحاولة مفيدة عندما يكون الخطأ مؤقتًا، مثل بعض أخطاء الشبكة أو حدود الاستخدام المؤقتة.

لكن إعادة المحاولة ليست حلًا لكل خطأ.

على سبيل المثال:

- `Timeout` قد يستحق إعادة المحاولة وفق تصميم العملية.
- `Invalid Input` يحتاج إلى تصحيح البيانات، وليس إعادة المحاولة بلا تغيير.
- `Unauthorized` يحتاج إلى معالجة المصادقة أو الصلاحيات.
- فشل حفظ نتيجة AI يحتاج إلى حماية من تكرار توليد النتيجة أو تكرار حفظها.

يجب أن تكون سياسة إعادة المحاولة مناسبة لنوع الخطأ، مع حدود واضحة، وتجنب التكرار غير المقصود.

# 🧪 LAYER 10 — Integration Testing

## 12. Test the Complete System

بعد بناء المكونات، يجب اختبارها معًا.

لا يكفي أن نرى أن كل Node في n8n نجحت منفردة، أو أن الواجهة تبدو جيدة، أو أن قاعدة البيانات تحتوي على جداول صحيحة.

يجب التأكد من أن رحلة المستخدم الكاملة تعمل كما هو متوقع.

### Example: PlanCraft AI Integration Test

أرسل طلبًا تجريبيًا، ثم تحقق من الآتي:

1. هل تم التحقق من مدخلات المستخدم؟
2. هل حُفظ الطلب في `project_requests`؟
3. هل حصل التطبيق على `request_id` الصحيح؟
4. هل وصل الطلب إلى Webhook؟
5. هل قرأ n8n الطلب الصحيح؟
6. هل أُرسل السياق الصحيح إلى AI؟
7. هل كانت مخرجات AI صالحة؟
8. هل حُفظت الخطة في `project_plans`؟
9. هل تم تحديث حالة الطلب؟
10. هل استرجع التطبيق الخطة المحفوظة؟
11. هل ظهرت النتيجة الصحيحة للمستخدم؟
12. ماذا حدث عند فشل إحدى الخطوات؟

### 12.1 Test More Than the Happy Path

يجب اختبار الحالات السلبية أيضًا.

| Test Case | Expected Behavior |
|---|---|
| إرسال طلب صحيح | حفظ الطلب وبدء المعالجة |
| غياب `request_id` | رفض الطلب برسالة واضحة |
| معرّف غير موجود | عدم إنشاء خطة لطلب غير موجود |
| مخرجات AI غير صالحة | عدم حفظ نتيجة غير صالحة |
| فشل الاتصال بقاعدة البيانات | تسجيل الفشل وعدم إعلان النجاح |
| تكرار الطلب | منع تكرار الأثر غير المقصود |
| فشل مؤقت في خدمة خارجية | التعامل معه وفق سياسة إعادة المحاولة |
| عدم اكتمال المعالجة | عرض حالة مناسبة بدل نتيجة وهمية |
| عدم امتلاك الصلاحية | منع الوصول غير المسموح |
| نجاح حفظ الخطة | عرض الخطة الفعلية المحفوظة |

### 12.2 Verify the Persisted Result

من أهم قواعد التكامل:

> Do not verify only that the request was sent. Verify that the intended result was persisted and can be retrieved.

قد يصل الطلب إلى n8n بنجاح، لكن عملية حفظ النتيجة قد تفشل.

لذلك، يجب التحقق من قاعدة البيانات ومن واجهة التطبيق، وليس من سجل Webhook وحده.

# 🐞 LAYER 11 — Debugging the Integration

## 13. Debug Systematically

عندما لا يعمل النظام، لا تغيّر عدة أشياء في الوقت نفسه.

ابدأ من نقطة دخول الطلب، ثم تتبّع البيانات خطوة بخطوة.

### Debugging Sequence

**Step 1 — Frontend**

- هل استقبل النموذج البيانات؟
- هل تحقّق من الحقول المطلوبة؟
- هل أرسل الطلب الصحيح؟

**Step 2 — Server-Side Function**

- هل استُدعيت الوظيفة؟
- هل وصلتها المدخلات؟
- هل تستخدم عنوان Webhook الصحيح؟
- هل تتعامل مع الاستجابة والأخطاء بشكل صحيح؟

**Step 3 — Webhook**

- هل وصل الطلب؟
- هل استخدم HTTP Method الصحيح؟
- هل وصل JSON بالشكل المتوقع؟
- هل عنوان الاختبار أو الإنتاج صحيح؟

**Step 4 — n8n Workflow**

- ما آخر Node نجحت؟
- ما أول Node فشلت؟
- هل البيانات الخارجة من كل Node صحيحة؟
- هل التعبيرات `Expressions` تشير إلى المسارات الصحيحة؟

**Step 5 — AI Processing**

- هل أُرسل السياق الصحيح؟
- هل استجاب النموذج؟
- هل شكل المخرجات صحيح؟
- هل اجتازت النتيجة التحقق؟

**Step 6 — Database**

- هل نُفذت عملية الحفظ؟
- هل كانت القيود أو الصلاحيات سببًا للفشل؟
- هل حُفظ السجل الصحيح؟
- هل تكررت النتيجة؟

**Step 7 — Frontend Result**

- هل استرجع التطبيق النتيجة الصحيحة؟
- هل يعتمد على حالة المعالجة الفعلية؟
- هل يعرض الخطأ عند الحاجة؟
- هل يعرض بيانات حقيقية بدل بيانات تجريبية؟

### Debugging Table

| Symptom | Possible Cause | What to Check |
|---|---|---|
| Webhook لا يستقبل الطلب | URL أو HTTP Method غير صحيح | Request URL, Method, Workflow status |
| `request_id` فارغ | اختلاف أسماء الحقول أو مسار التعبير | Input JSON and expressions |
| AI لا يعيد نتيجة | مشكلة في مزود AI أو إعداداته | Credentials, model, provider response |
| Structured Output Parser يفشل | المخرجات لا تطابق البنية المطلوبة | Schema and raw model output |
| Supabase لا يحفظ النتيجة | صلاحيات أو قيود أو بيانات غير صالحة | Error message, constraints, access policies |
| الطلب مكتمل لكن لا توجد خطة | تحديث الحالة قبل نجاح الحفظ أو خلل في منطق التنفيذ | Node order and database records |
| تظهر خطط مكررة | إعادة إرسال الطلب دون حماية | Unique constraints and idempotency |
| التطبيق يعرض رسالة خطأ رغم نجاح المعالجة | مهلة اتصال أو سوء معالجة الاستجابة | Server logs, workflow execution, saved result |
| التطبيق يعرض نتيجة قديمة | استرجاع سجل غير صحيح أو بيانات غير محدّثة | Request ID and query conditions |

### Engineering Principle

> Debug the data flow, not just the visible error.

رسالة الخطأ تخبرنا أن هناك مشكلة، لكن تتبّع البيانات يساعدنا على معرفة أين حدثت ولماذا.

# 🛠️ LAYER 14 — Practical Exercise

## Exercise: Complete a Real Integration

اختاري مشروعًا سبق بناؤه، مثل PlanCraft AI أو نظام تأهيل العملاء العقاريين، وراجعي تكامل مكوناته.

لا يكفي أن يكون لديك تطبيق جميل أو Workflow يعمل بصورة منفردة.

المطلوب هو إثبات أن البيانات تتحرك من البداية إلى النهاية بصورة صحيحة.

### Tasks

1. ارسمِي مسار البيانات من المستخدم حتى النتيجة النهائية.
2. حددي مسؤولية كل مكوّن.
3. وثّقي شكل الطلب الذي يرسله التطبيق.
4. وثّقي الاستجابة التي يتوقعها.
5. نفّذي اختبارًا لمسار النجاح.
6. نفّذي اختبارًا لمدخلات غير صحيحة.
7. اختبري ما يحدث عند فشل خدمة خارجية.
8. تحققي من عدم إنشاء سجلات مكررة عند تكرار الطلب.
9. تحققي من حفظ النتيجة في قاعدة البيانات.
10. افتحي التطبيق وتحققي من عرض النتيجة الفعلية.
11. وثّقي مشكلة واحدة واجهتك وكيف شخصتِها.
12. أكملي `Build and Integration Report`.

### Deliverables

- Architecture أو Data Flow Diagram.
- Data Contract.
- Integration Test Table.
- Build and Integration Report.
- دليل على نجاح المسار الأساسي.
- قائمة بالمشكلات المتبقية، إن وجدت.

# 🧠 Final Engineering Mindset

أثناء بناء الحل، لا تسألي فقط:

- هل انتهيت من بناء الواجهة؟
- هل عمل الـ Workflow؟
- هل نجح استدعاء AI؟
- هل قاعدة البيانات متصلة؟

بل اسألي:

- هل ينفّذ النظام متطلبات المستخدم فعلًا؟
